## 0. 结论先行

1. **按矩阵 45 个功能点计，现有契约只完整覆盖 4 个**（主动注册、实时预览、回放地址、8 方向云台），部分覆盖 1 个（通道目录），**缺口 40 个**。其中 **18 个是 P0**，决定这套方案能不能真正替代"只能看画面"的现状。
2. **最大的技术风险不在功能数量，而在公网部署下的 RTSP 可达性**：设备主动注册上报的是 SDK 端口，RTSP 554 通常没有被 NAT 映射。若此路不通，公网场景下"预览/回放走 RTSP"这个已有共识会失效，必须提前拍板回退方案（见 Q5）。
3. **抓图直传是本方案的核心卖点，也是最容易被低估的模块**：它不是"平台发一条指令"，而是"配置设备通过 **HTTP/HTTPS 直传到平台端点**"（FTP 仅老固件兜底），能省掉整条拉流链路的上行带宽。
4. 建议分 **3 期** 交付（§8），一期一次性交付全部 18 个 P0，约覆盖用户 80% 的日常操作动作。

## 1. 产品目标

补齐后，平台从"看国标画面的平台"变成"能管大华设备的平台"。具体能打开这 5 个原来做不到的场景：

| # | 目标 | 原来为什么做不到 | 补齐后的效果 |
|---|---|---|---|
| G1 | **值班员不必再登录设备 Web 或大华客户端** | 预置位、巡航、图像参数在国标协议里没有对应信令 | 预置位/云台/画面参数全部在平台内完成，一次登录看所有品牌 |
| G2 | **公网/4G 设备能接进来** | 国标要求设备可被平台路由到，NAT 后无解 | 设备主动注册，只要有出网能力即可接入，无需公网 IP 或端口映射 |
| G3 | **批量装维从"逐台点开看"变成"扫一遍就建完"** | 无局域网发现，每台设备手填 IP/账号 | 组播探测批量发现同网段设备，一次录入 |
| G4 | **抓图零拉流**：报警截图不占上行带宽 | 只能平台拉流截帧，1 路 1080P 常驻约 2~4 Mbps | 设备用 HTTP/HTTPS 直传到平台端点，单张 JPG 约 100~300 KB；设备侧按事件类型过滤，平台端不做二次筛选 |
| G5 | **报警从"事后翻录像"变成"事中响应"** | 无 SDK 报警订阅，只能轮询或人工发现 | 移动侦测/遮挡/报警输入实时进平台，可联动抓图与弹窗 |

**非目标**：不做营销意义上的"全兼容"，本 PRD 只承诺大华 NetSDK 已支持且设备型号支持的能力，型号差异必须如实呈现给用户。

## 3. 功能矩阵

**覆盖口径**：✅ 现有契约已完整覆盖 ｜ ⚠️ 部分覆盖，需补 ｜ ❌ 缺口

### 3.1 模块一：设备发现与主动注册

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 局域网设备发现（组播/广播探测） | ❌ | P0 | **仅限同一广播域**。跨网段/三层网络无效；需处理多网卡选路、探测超时、重复应答；结果需含 IP/型号/序列号/固件版本 |
| 设备主动注册（平台监听） | ✅ | P0 | 已实现 `ConnectMode.SERVER` + `RegisterListener` + `DeviceRegisterTable`。缺：**注册 SN 与平台设备记录的绑定**、注册密钥/白名单校验、断线后地址刷新 |
| 注册状态可视化 | ❌ | P0 | 占用/释放监听端口是全局操作，必须能回答"监听起来没有、端口几号、收了多少注册"；端口冲突要给出明确中文原因 |
| 发现结果入库策略 | ❌ | P1 | 发现即自动建设备 vs 只列"待添加"清单，见 Q7 |

### 3.2 模块二：通道、预览、回放、下载

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 通道目录获取 | ⚠️ | P0 | 现实现只按"通道数"生成"通道 1..N"，**没有真实通道名称、在线状态、PTZ 能力位、是否支持对讲**。NVR 下挂 IPC 需区分自身通道与 IPC 通道 |
| 实时预览 | ✅ | — | RTSP 拉流。约束：设备须开 RTSP（默认 554，须可配置）；子码流通道号 = 主码流通道号 + 通道总数，通道总数不是设备能力则是错的 |
| 录像检索（有录像的时间段清单） | ❌ | P1 | **下载的前置依赖**，用户没提但绕不开。NVR 需按通道查；结果要合并连续段，否则时间段碎片化 |
| 录像回放 | ✅ | — | RTSP 回放。约束：不支持倍速/暂停/拖动（RTSP 播放控制能力有限，倍速需 SDK 取流或前端处理）；时间必须按设备本地时区 |
| 录像下载到服务器 | ❌ | P1 | 走 SDK 文件下载（非 RTSP），可断点续传；需落盘目录、配额、任务队列、进度可查；公网下受设备上行带宽限制 |

### 3.3 模块三：云台控制（11 个子功能）

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 8 方向 + 变倍 + 停止 | ✅ | — | 已实现。速度 0~255 → 厂商 1~8 折算；"停"需对所有方向逐一发送才可靠（已在实现中处理） |
| 预置位（设置/调用/删除/列表） | ❌ | **P0** | 值班最高频操作。约束：预置位号范围由型号决定（常见 1~300）；调用是**异步**的，转到位才生效，UI 需给"转动中"反馈；断电可能丢 |
| 云台限位（左右限位） | ❌ | P1 | 与水平旋转绑定；设定时需在当前位置标定，误设会导致球机撞限位 |
| 水平旋转（连续扫描 + 区间） | ❌ | P1 | 依赖限位；速度与方向独立于 8 方向控制 |
| 巡航组（增删点/停留时间/速度/启停） | ❌ | P1 | 组内成员引用预置位号，**预置位被删会导致巡航组失效**，需一致性校验 |
| 云台速度配置（方向/线扫/预置位/巡航） | ❌ | P1 | 四类速度是独立参数，不可混用一个；写入后是否立即生效依型号而定 |
| 云台重启 | ❌ | P1 | 重启后需重新登录会话，调用方需知道"3 分钟内不可用" |
| 巡迹（自动学习轨迹） | ❌ | P2 | 需"开始记录→人工操作→结束记录→保存"长流程，中途超时或断连会毁掉整条轨迹 |
| 开机动作 | ❌ | P2 | **上电时触发**（无/预置位/巡航/巡迹/水平旋转）。误配会导致设备上电即乱转，需二次确认。与空闲/定时任务**同配置、不同字段** |
| 空闲动作 | ❌ | P2 | **空闲 N 秒后触发，无固定时刻**。需设阈值；与人工操作抢占，实现上要能被打断。与开机/定时任务**同配置、不同字段** |
| 定时任务（按时间表执行动作） | ❌ | P2 | **固定时刻触发**（如 08:00 转到某预置位），与"空闲动作"语义不同。时区、夏令时、任务冲突（同一时刻两条规则）需明确优先级。与开机/空闲**同配置、不同字段** |

> **实现提醒（务必转达开发）**：开机动作 / 空闲动作 / 定时任务 三项落在 `CFG_CMD_PTZ_AUTO_MOVEMENT`（`"PtzAutoMovement"`）**同一份配置结构**里，但**语义与字段互不相同** —— 上电触发 / 空闲计时触发 / 按时刻表触发。
> **不可合并成一个"自动动作"功能实现**：合并会导致 (a) 三种触发条件无法独立开关；(b) 一份配置写入互相覆盖；(c) 现场排查时无法区分"为什么球机没转"。必须按三个独立字段分别读写，对外暴露三个独立能力点。

### 3.4 模块四：抓图直传（设备 → 平台 HTTP 端点）

> **主链路已定**：**平台提供 HTTP 接收端点 + 配置设备 HTTP 直传**为默认路径（配置项 `NET_CFG_PICTURE_HTTP_UPLOAD_INFO`，枚举 `NET_EM_CFG_PICTURE_HTTP_UPLOAD = 1609`）；**FTP 仅作老固件兜底**，不作为新部署方案。

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 立即抓图并直传服务器 | ❌ | **P0** | 本质是**配置设备的上传目标 + 触发一次上传**，不是平台发指令收图。默认走 HTTP/HTTPS 直传，FTP 仅老固件兜底。型号能力差异大，部分型号仅支持定时/报警触发，不支持"立即抓一张" |
| 上传目标配置（HTTP/HTTPS 直传） | ❌ | **P0** | ① 支持 HTTP/HTTPS（`bHttpsEnable`）与 Basic 鉴权（`bAuthEnable`）；② `stuUploadServerList[64]` 可配**多服务器**（生产 + 备份同传）；③ `stuUploadServerList[].szEventType[]` 在**设备侧**按事件类型过滤 —— 流量控制在设备端完成，平台端不做二次过滤，这是"低流量"诉求的真正落点；④ **必须与设备约定 Content-Type**：`bEnableFormdata=true` → `multipart/form-data`（单张，常规）；`false` → `multipart/x-mixed-replace`（流式连续上传，接收端解析方式完全不同）。**约定不一致会直接解析不出图片** |
| 定时抓图上传 | ❌ | P0 | 需配置间隔、图片大小/质量、通道 |
| 报警联动抓图上传 | ❌ | P0 | 与模块七联动，是"报警带图"的唯一低成本实现 |
| 平台侧接收端点与元数据入库 | ❌ | **P0** | **职责边界 = 接收 + 落盘 + 入库元数据；不含图片解码 / 缩略图 / AI 识别**（超出即膨胀为"图片处理服务"，范围失控）。按约定的 Content-Type 解析后就地写对象存储（不落中间目录），元数据（设备 ID/通道/时间/触发类型/来源服务器序号）入库。**这是 P0 中唯一的平台侧新增组件**（可能需独立端口/独立鉴权），排期时必须单独列出，见 Q1 |

### 3.5 模块五：喊话与对讲

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 单工喊话（平台 → 设备扬声器） | ❌ | **P0** | 需"音频通道"抽象，不能塞进现有 `DeviceAccessProvider` 的同步方法。音频编码/采样率须与设备匹配；浏览器端需 WebRTC 网关（媒体服务承担）。公网下延迟与抖动明显 |
| 双工对讲 | ❌ | P1 | 在单工基础上加回传，**NAT 双向打洞 + 回声消除**是难点；公网不建议作为首批交付项 |
| 设备是否支持对讲的能力标识 | ❌ | P0 | 通道目录须带"支持对讲"标识，否则 UI 会给出点了没反应的按钮 |

### 3.6 模块六：相机配置（19 个配置项，按参数组归并为 12 行）

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 亮度 / 对比度 / 饱和度 / 色彩抑制 | ❌ | **P0** | 四项为一组，读写成套；取值范围厂商定义（常见 0~100），不可假定 |
| 伽马 / 锐度 / 锐度抑制 | ❌ | **P0** | 同组读写 |
| 视角：正常 / 倒影(180°) / 镜像(左右) / 走廊(90°) | ❌ | **P0** | 为**互斥组合**，不是独立开关；走廊模式会改变分辨率与宽高比，前端播放器需适配 |
| 曝光（自动/手动、快门、增益、抗闪烁） | ❌ | P1 | 自动模式下部分参数只读；抗闪烁需按 50Hz/60Hz 区分 |
| 背光（背光补偿 / 宽动态 / 强光抑制） | ❌ | P1 | 三者可能互斥，同时开会互相覆盖 |
| 白平衡（自动/手动/场景） | ❌ | P1 | 手动模式需色温值 |
| 日夜模式（自动/彩色/黑白/时间表） | ❌ | P1 | 自动模式依赖光敏阈值；时间表需下发时段 |
| 数字变倍 | ❌ | P2 | 与云台光学变倍是两个概念，UI 必须区分，否则用户会认为是"变倍不灵" |
| 聚焦（自动/手动/变倍后自动聚焦） | ❌ | P2 | 手动聚焦值型号相关；失焦是现场最常见投诉 |
| 补光灯（模式/亮度/灵敏度） | ❌ | P2 | 亮度过高会过曝并影响邻居；需给建议值 |
| 透雾 | ❌ | P2 | 部分型号为"光学透雾"硬件能力，软件开关无效 |
| **能力查询（型号能力位）** | ❌ | **P0** | **横切依赖**：以上 19 项在不同型号上开关不同，必须"先读能力→动态生成表单"，否则 UI 会给出一堆点了报错的项 |

### 3.7 模块七：报警接收

| 功能点 | 契约覆盖 | 优先级 | 关键约束 / 难点 |
|---|---|---|---|
| 报警订阅（移动侦测/视频遮挡/报警输入/视频丢失/断网/硬盘故障等） | ❌ | **P0** | 异步回调，需**长驻会话**；公网 SERVER 模式下回调复用已建连接，不受 NAT 影响（这是 SERVER 模式的一个隐性优势） |
| 报警事件标准化与推送 | ❌ | P0 | 需统一事件模型（设备/通道/类型/时间/图片路径）；风暴抑制与去重（同通道 1 秒内多次移动侦测） |
| 布防 / 撤防 | ❌ | P1 | 与"报警订阅"不同层：订阅是平台侧开关，布防是设备侧状态，两者不一致会出现"订阅了但没报警" |
| 报警联动（抓图 / 录像片段 / 第三方推送） | ❌ | P1 | 抓图联动见模块四；录像片段联动依赖模块二下载能力 |
| 报警落库与保留期 | ❌ | P1 | 见 Q2 |

**统计**：45 个功能点 = ✅ 4 个 + ⚠️ 1 个 + ❌ 40 个。按优先级：**P0 = 18**、P1 = 16、P2 = 8；另有 3 项（实时预览、回放、8 方向云台）已交付，不再排期。

## 4. 两种部署场景差异

| 模块 | 局域网（CLIENT，平台主动连） | 公网（SERVER，设备主动注册） | 差异结论 |
|---|---|---|---|
| 一、设备发现 | ✅ 可用（组播/广播可达） | ❌ **不可用**（组播不跨网段） | 公网只能靠主动注册，两条路互补而非替代 |
| 一、主动注册 | 可用但不必要（多一道依赖） | ✅ **必需**，唯一可行方式 | 需设备侧配置平台地址+注册端口，装维需文档支撑 |
| 二、通道目录 | ✅ 走配置地址登录 | ✅ 走注册表回填地址 | 无本质差异，但 SERVER 下地址是易失的，需每次取注册表实时值 |
| 二、实时预览 / 回放 | ✅ RTSP 直连 554 | ⚠️ **高风险**：注册上报的是 SDK 端口，**RTSP 554 通常未做 NAT 映射** | **本方案最大风险点，见 Q5。** 若 RTSP 不可达，公网场景下预览/回放整体失效 |
| 二、录像下载 | ✅ 带宽充裕，可批量 | ⚠️ 受设备上行带宽限制，需限速与排队 | 公网下"边下边播"要降级为"后台任务" |
| 三、云台控制 | ✅ 指令量小、时延低 | ✅ 技术上可行，但 RTT 高，"按住转"体验差 | 公网下需前端做指令合并（只发最后一次方向），否则指令风暴 |
| 四、抓图直传 | ✅ HTTP 直传可用，但局域网带宽本就充裕，价值感低 | ✅ **价值最高**：设备 HTTP/HTTPS 直传平台端点，省掉整条拉流上行，是公网部署的最优截帧方案 | 结论不变（公网优先级高于局域网）。**新增公网前置条件**：平台接收端点必须有设备可达的 HTTP/HTTPS 地址（域名或 IP:端口），启用 HTTPS 时还需设备信任的证书 —— 设备不认自签证书会静默上传失败 |
| 五、喊话 / 对讲 | ✅ 推荐首批交付 | ⚠️ NAT 双向 + 抖动 + 回声，双工尤其难 | 单工喊话公网可试，**双工对讲建议仅承诺局域网** |
| 六、相机配置 | ✅ 低频小包，无压力 | ✅ 可行，注意首次读全量参数耗时长（超时值需放宽） | 无本质差异 |
| 七、报警接收 | ✅ 回调走已建连接 | ✅ **反而是优势**：回调复用设备主动建的长连接，天然穿透 NAT | 公网报警到达率可能比局域网轮询更稳 |

**部署选型建议（给集成商）**：

- 设备与平台同网段 → **CLIENT**，最简单、能力最全。
- 设备在 NAT/4G 后 → **SERVER**，但必须确认三件事：设备能出网、SDK 端口可达（注册方向天然满足）、**RTSP 端口是否需要额外映射**。
- 混合部署 → 一个平台同时开 CLIENT 与 SERVER 两条路，按设备粒度选；监听端口是全局资源，只能起一份。

## 5. 需求边界（明确不做）

| 不做 | 理由 |
|---|---|
| 视频转码 / 转封装 / 画面合成 | 由媒体服务负责，超出本模块边界；本模块只产出地址与指令 |
| 平台侧解析 PS/码流 | 已有共识。一旦为了公网回退而破例，需单独评估（见 Q5） |
| AI 结构化分析（人形/车牌/人脸比对） | 属算法域，设备侧已有智能功能，平台只需接收其结果型报警 |
| 设备端存储管理（SD 卡/硬盘配额、录像计划、格式化） | 属设备自身运维，风险高（误操作丢录像），不纳入 |
| 固件升级 / 批量升级 | 高风险不可逆操作，需独立产品线评审 |
| 设备端用户与权限管理 | 平台只维护一个专用账号，不做设备侧账号体系 |
| 设备发现跨网段 / ONVIF 发现 | 组播本身不跨三层；ONVIF 属另一协议栈，不在本期 |
| 海康 / 宇视适配 | 各自独立 `sdk-*` 模块，本期只做契约与能力矩阵的可复用性 |
| 移动端专用交互 | 现有前端框架已覆盖，不做大华专属适配 |
| 巡航组/预置位的可视化拖拽编辑器 | 一期只做表单 + 数字输入，拖拽见 Q4 |
| 图片解码 / 缩略图 / OCR / AI 二次识别 | 抓图接收端点只做「收 + 落盘 + 入库元数据」；解码与缩略图会引入图像库与 CPU 开销，AI 属算法域 |

## 6. 异常处理统一口径（PM 级约定，避免各模块各写一套）

| 场景 | 约定 |
|---|---|
| 查询类失败（目录、能力、注册表） | 返回空集合 / `false`，**不抛异常**；必须打可读日志（哪个设备、什么原因） |
| 控制类失败（云台、配置写入、重启） | **抛异常**并带中文原因，禁止静默返回成功 |
| 设备不支持该能力 | 明确返回"设备/型号不支持该能力"，**不做静默降级**（静默降级会让现场误判为设备故障） |
| 异步类（注册、报警、下载任务） | 走事件/消息，不让调用方阻塞等待 |
| 超时 | 登录 5s 量级、指令 3s 量级、读全量图像参数放宽到 10s 量级；所有超时值可配置 |
| 原生库缺失 / 加载失败 | 不影响国标主链路；大华能力整体降级为"不可用"，并在运维界面给出可操作的中文提示 |

## 7. 待确认问题（需拍板）

| # | 问题 | 影响范围 | 建议方案 |
|---|---|---|---|
| **Q1** | 抓图文件存哪、怎么入库？保留多久？ | 模块四全量 | **默认 HTTP/HTTPS 直传到平台接收端点**（FTP 仅老固件兜底）；接收端按约定 Content-Type 解析后就地写对象存储，元数据入库，不落中间目录。**需额外拍板**：HTTPS 用公信证书还是允许自签（设备是否内置信任链）；多服务器（`stuUploadServerList[64]`）是否同时启用生产+备份。保留期与 Q2 报警一致（90 天） |
| **Q2** | 报警是否落库？保留期？是否需要带图片/录像片段？是否要 Webhook/MQ 推送第三方？ | 模块七 + US-15 | 必须落库（否则无法事后检索）；带图；保留 90 天；提供 Webhook |
| **Q3** | 对讲音频编码与链路怎么定？是否允许引入 WebRTC 网关？单工喊话能否用"设备端播放预置音频"简化？ | 模块五 | 一期只承诺局域网单工；音频编码待架构师按设备能力确认 |
| **Q4** | 巡航组 / 预置位 / 定时任务是否需要可视化配置界面，还是先只做 API？ | 模块三 P1/P2 项 | 一期只做表单，不做拖拽；定时任务暂缓到三期 |
| **Q5** | **公网 SERVER 模式下 RTSP 不可达时，是否接受"SDK 取流 + 服务端转封装"作为回退？** | 模块二（**最高风险**） | 这是唯一会推翻"平台不解析 PS 流"共识的决策点。建议：先做实测，若 RTSP 确实不通，再评估是否在媒体服务侧（而非本模块）加转封装 |
| **Q6** | 相机配置是否需要"同型号一键套用"？ | 模块六 + US-05 | 建议做，实现成本低、现场价值高 |
| **Q7** | 局域网发现的结果是自动入库，还是只列"待添加"清单由人确认？ | 模块一 | 建议"发现即列清单，一键批量添加"，不要全自动（误发现邻居设备会污染设备表） |
| **Q8** | 关于 SERVER 模式：一个监听端口能否同时服务多台设备？是否需要注册密钥/白名单？ | 模块一 | 必须支持多设备复用同一端口；注册白名单是安全刚需，建议 P0 |
