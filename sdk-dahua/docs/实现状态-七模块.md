### 0.1 本轮发现的真机真相（都写进代码注释了）

1. **IPC 的云台通道号是 0，不是 1**
   `byDVRType=20 (NET_IPC_SERIAL)`。用 1 去控 **不报错、SDK 返回 true、设备什么都不做**。
   实测同一台 IPC：通道 0 UP 后 tilt -111→-150、变倍 zoom 6→11；通道 1 前后完全一致。
   → `DahuaSdk.Session#ipc()` + `DahuaCapabilityService#sdkChannel`

2. **配置 JSON 结构是 `params.table`，且 table 可能是对象也可能是场景数组**
   `VideoInOptions` → `params.table` 是对象；`VideoInExposure` → 是 Day/Night/Normal 等**场景数组**（不是通道）。
   只查顶层字段会永远读到 null（表现为「能力位说有、值全空」）。

3. **同一个字段在配置里出现 20+ 次，第一组是只读快照**
   探针把全部 `Flip` 写成 true 后，只有第一组保持 false。
   读值必须优先取 `NormalOptions`（白天场景），否则「写入成功、读回永远不变」。

4. **`CLIENT_SetNewDevConfig` 返回 true ≠ 值改了**
   本机对视角字段（Flip/Mirror/Rotate90）就是返回成功但不生效。
   → 写入后**自动回读校验**，没生效就返回 `saved:false` + `rejected`，
   绝不显示「保存成功」。

5. **`CLIENT_GetNewDevConfig` 失败时不填错误码**（`nError=0`）
   所以「配置项不支持」只能按「读不到」这个事实判断，不能靠错误码。

6. **`CLIENT_GetLastError` 是线程级"最后一次错误"，成功后不清零**
   调成功的接口后读它，拿到的是上一次失败的残留码。
   只在 `返回 false` 之后读才有意义 —— 否则会得出「成功了但错误码是 0x80000017」这种自相矛盾的结论。

7. **预置点指令返回 true ≠ 云台动了**（曾被误判成「型号不支持」）
   本机 IPC 上 `POINT_SET` / `POINT_MOVE` / `POINT_DEL` **全部返回 true**，
   但 15 秒连续采样 `pan` 恒定不变。当时代码据此判断「该型号没有预置点」，
   **结论是错的** —— 设备 Web 界面明明有「預置點1」。
   真因见第 8 条。

8. **绝对定位精确可用**（独立能力，不再用于预置点兜底）
   `NET_EXTPTZ_MOVE_ABSOLUTELY(69)` + `PTZ_CONTROL_ABSOLUTELY`：
   pan 1660 → 3（误差 0）、定位到 (1200,-100,20) 精确到位。
   注意 `EXACTGOTO(67)` 传 `null` 结构体会被当成**全零坐标**，表现为「跳到原点」，不要拿它做绝对定位。
   早期曾用它替代预置点（平台存坐标方案），现已移除 —— 设备本身支持预置点。

9. **预置点读写的三条独立接口，型号实现哪条完全不可预测**（本机踩坑总结）
   | 接口 | 本机结果 | 能力 |
   |---|---|---|
   | `CLIENT_QueryDevState(NET_DEVSTATE_PTZ_PRESET_LIST=0x57)` | ✅ **可用** | 带**名称 + 坐标** |
   | `CLIENT_GetConfig(NET_EM_CFG_PTZ_PRESET=1011)` | `0x80000007` | 部分型号支持 |
   | `"PtzPreset"` JSON 配置项 | `0x80000018` | 部分型号支持 |

   早期只试了第 3 条，读不到就断言「设备不支持预置点」，**结论完全相反** ——
   设备 Web 界面有「預置點1」，第 1 条接口也能读到 `编号=1 / 名称=預置點1 / 坐标=1113,-150,1`。
   → `DahuaExtAccess#listPresets` 现在**三条依次试**，第一条有结果就用

   **名称编码不统一，不能写死**：IPC-HFW 系列实测是 **UTF-8**（`E9 A0 90 E7 BD AE E9 BB 9E 31`
   = 「預置點1」），按 GBK 解得到「闋愮疆榛�1」；部分老固件返回 GBK。
   早期把 `decodeGbk()` 写死，用户看到的就是那串乱码。现在用 `decodeName()`
   按「严格 UTF-8 能否解通」自动判定（UTF-8 结构约束强，GBK 碰巧合法的概率极低）。

   **结构体数组必须分配在原生内存**：`new Memory(unit * max)`，
   把 Java 对象数组直接传进 SDK 拿不到数据。

10. **预置点指令的四个必守细节**
    | 细节 | 错了会怎样 |
    |---|---|
    | **预置点号传 `lParam2`**（不是 `lParam1`） | 返回 true，但操作的是「预置点 0」，设备什么都不做 |
    | `szReserve` 必须显式清零 | JNA 的 `byte[]` 默认 `null`，设备返回 `0x80000015` |
    | 预置点号 **1 基** | 传 0 返回 `0x80000007`（参数不合法） |
    | `dwStop` 必须为 **0** | 传 1 同样返回 `0x80000007` |

    **参数位置是本模块最难发现的坑**。真机对比（用 `QueryDevState(0x57)` 读清单判定）：
    ```
    SET  param1=30 param2=0   → 返回 true，清单里没有 30
    SET  param1=0  param2=31  → 返回 true，清单出现 31   ★
    GOTO param1=31 param2=0   → 返回 true，位置不变
    GOTO param1=0  param2=31  → 返回 true，转到预置点 31 的位置  ★
    ```
    旁证：SDK Demo 里变倍的速度也传 param2
    （`CLIENT_DHPTZControlEx(..., NET_PTZ_ZOOM_ADD_CONTROL, 0, lParam2, 0, 0)`）。

    传错参数时会得到「说成功了但设备上什么都没有」这种最坑的现象，
    而且对已存在编号会看起来成功（实际回了原位）—— 极易误判成「型号不支持」。

    **`0x80000015` 在预置点场景的真实含义是「该编号没有预置点」**，不是「型号不支持」。
    实测：有预置点 1 时 GOTO 1 成功且精确回位（连做 3 次误差 0）；GOTO 不存在的 5 号返回此码。

11. **写配置的 payload 只能是业务层，写整包会永久污染设备**（血的教训）
   `CLIENT_GetNewDevConfig` 返回完整响应包
   `{"id":..,"params":{"table":{业务}},"result":true,"session":..}`，
   但 `CLIENT_SetNewDevConfig` 只接受 `{"params":{"table":{业务}}}`。
   把整包原样写回去，设备会把 `id`/`result`/`session` **当成业务字段存进 table**，
   每写一次多嵌一层（实测 `TimeSection` 在 JSON 里出现 5 次）。
   更糟的是**写入是 merge 语义** —— 没出现在 payload 里的字段保留旧值，
   所以嵌进去的垃圾**写不回去也删不掉**，最后只能用 `CLIENT_DeleteDevConfig` 删掉整条配置项。
   → `DahuaExtAccess#writeConfig` 现在会**自动剥壳**，只写业务层；配套 `businessLayer()` 幂等可用

10. **推送命令前先确认「这个型号到底能不能写」**
    实测这台 IPC 的 `Record` 配置**整条只读**：连 `PreRecord` 这种普通字段
    写入都返回 true 但值不变（`TimeSection` 同理）。`Alarm.Enable` 也是同样表现。
    → 所有配置写入都必须**回读校验**，失败时如实报「设备不接受」，
    绝不显示「保存成功」

### 0.3 预置点：只走设备（平台不再存副本）

**曾经错得很彻底**：早期用「`PtzPreset` 配置项能否读到」当能力位，
读不到就断定「该型号没有预置点」，于是做了一套「平台存 (pan,tilt,zoom) + 绝对定位回位」的兜底。
实际设备 Web 界面有「預置點1」，`QueryDevState(0x57)` 也能读到 ——
**把「能不能列清单」当成了「支不支持预置点」**。

**兜底已移除**。设备有的就用设备的，平台副本只会带来：
- 两份数据不同步（设备上改了、平台上没改）
- 假数据（设备上没有、平台却显示存在）
- 多一层维护成本，功能还不如设备侧（设备侧掉电不丢、Web 界面可见、其他客户端可用）

| 操作 | 实现 |
|---|---|
| 设置 | `setPreset`（`NET_PTZ_POINT_SET_CONTROL`，1 基） |
| 调用 | `gotoPreset`（`GOTOPRESET(71)` + 结构体，1 基，`dwStop=0`） |
| 删除 | `deletePreset`（`NET_PTZ_POINT_DEL_CONTROL`） |
| 列表 | `QueryDevState(0x57)` → `GetConfig(1011)` → `PtzPreset` 配置项，三条依次试 |

平台唯一保留的预置点数据是**别名**（`gb_preset.name`）——
设备不存这个，只有平台知道。表里的 `pan/tilt/zoom` 三列已随方案一起移除。

**真机验证**：

```
设备侧预置点 1 坐标 (1113, -150, 1)   ← QueryDevState(0x57) 读到的
转开 4 秒 → 调用预置点 1 → 位置 (1113, -150)
与预置点 1 差值 [0, 0, 4]  → 精确回位
```

GOTO 连做 3 次，每次都精确回到 `pan=1113 tilt=-150`，误差 0。
调用不存在的 88 号：`0x80000015` → 提示「设备上没有这个编号的预置点」，
**不再有平台坐标兜底**（那会掩盖「编号本来就错」这个事实）。

**本机设备的能力边界**（实测，非推测）：

| 调用 | 结果 | SDK 错误码 |
|---|---|---|
| 登录 / 通道 | ✅ | — |
| 报警订阅 | ✅ 收到 10 类事件（0x2101 / 0x2102 / 0x2183 / 0x2123 …） | — |
| 设置/调用/删除预置位 | ✅ 可用（先前的「返回 true 但不动」是用了不存在的编号） | — |
| 读配置 `PtzPreset` | ❌ 配置项不存在（但 `QueryDevState(0x57)` 可用） | `0x80000018` |
| 绝对定位 `MOVE_ABSOLUTELY(69)` | ✅ 精确到位 | — |
| 扩展指令 `GOTOPRESET(71)` | ✅ 预置点存在时精确回位 | 编号不存在时 `0x80000015` |
| 抓图 `CLIENT_ManualSnap` | ❌ | `0x80000007` 用户参数不合法 |
| 读配置 `PtzTour` / `PtzLimit` / `PtzSpeed` | ✅ | — |

### 0.4 设备级控制：国标命令 → 大华接口对照

平台补齐了先前被 `sendControl` 一刀切拒绝的一批命令。封装在
`DahuaDeviceCtrl`（整机类）与 `DahuaConfigEditService`（配置开关类）。

| 国标命令 | 平台接口 | 大华实现 | 本机实测 |
|---|---|---|---|
| 设备信息 `DeviceInfo` | `POST /device/fetchinfo` | `CLIENT_GetSoftwareVersion` + 会话信息 | ✅ 可用 |
| 设备状态 `DeviceStatus` | `POST /device/fetchstatus` | `CLIENT_QueryDeviceTime`（同步） | ✅ 可用 |
| 校时 | `POST /control/synctime` | `CLIENT_SetupDeviceTime` | ✅ 可用 |
| 报警复位 `AlarmReset` | `POST /control/alarmreset` | `CLIENT_ControlDevice(CTRLTYPE_CTRL_CLEAR_ALARM)` | ✅ 可用 |
| 设备重启 `TeleBoot` | `POST /control/teleboot` | `CLIENT_ControlDevice(CTRLTYPE_CTRL_REBOOT)` | 未测（会断流，需人工确认） |
| 雨刷 `Wiper` | `POST /control/wiper` | `CLIENT_DHPTZControlEx2(NET_PTZ_LAMP_CONTROL)` | ⚠ 返回 true，需看画面确认 |
| 补光灯 `FillLight` | `POST /control/filllight` | 同上，`param2` 区分序号 | ⚠ 同上 |
| 录像开关 `Record/StopRecord` | `POST /control/record`<br>`POST /dahua/record/plan` | 改 `Record` 配置的 `TimeSection` | ❌ **该型号整条配置只读** |
| 布防/撤防 `Guard` | `POST /control/guard` | 改 `Alarm` 配置的 `Enable` | ❌ `Alarm.Enable` 只读 |
| 强制关键帧 `IFrame` | `POST /control/iframe` | **无对应接口** | ❌ 如实拒绝 |
| SD 卡格式化 | `POST /control/formatsdcard` | 本 SDK 版本无 `NET_SD_CARD_INFO` 结构 | ❌ 未接入 |

**只读配置的实测证据**（`RecordWriteProbe`，已删）：

```
原始 PreRecord=5
写入 PreRecord=6 → SetNewDevConfig 返回 true，nRestart=0
回读 PreRecord=5   ← 没变
写入 TimeSection 首段 6→3 → 返回 true
回读首段 "6 00:00:00-23:59:59"  ← 没变
```

连普通字段都写不进 → **不是计划字段受保护，是整条配置对该型号只读**，
与 §0.1 第 4 条（`SetNewDevConfig` 返回 true ≠ 值改了）同一类现象。

**设备录像计划的真实内容**（读得到，可作为排障依据）：

```
通道 0 的 6 个时段里只有第 1 段启用：类型 6（周六）00:00:00-23:59:59
其余 5 段类型 0 = 不录像
→ 「明明没开录像却在录」的真相就在这里：设备只配了周六，而周六整天都在录
```

**注意 `CLIENT_RecordStartEx` 不能用**：它录的是**平台机器的磁盘**，
不是设备 SD 卡，语义与国标 `Record` 不符。本机还返回 `0x80000203`（不支持）。
